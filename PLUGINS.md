# 🔌 External-plugin surfaces — recon report (v9.3, 2026-07-03)

Four parallel investigations into how third-party tooling (like this MCP) can extend the PICO stack,
plus the live-verified answer to "do plain Android apps work on the emulator?" (YES — they composite
as floating spatial panels; vision-verified after correcting a camera-framing error).

## 2D Panel Host — feasible: **yes**

YES — the PICO emulator has a first-class 2D-panel host, and it was proven live: launching com.android.settings via plain `am start` produced a fully composited Settings panel floating in the spatial viewport (screencap verified). The mechanism: PICO's forked WindowManager stamps every window with SpaceWindowAttributes and auto-assigns each 2D app task a spatial containerId (Settings got 45); the platform `spatial_container` service (com.spatial.app.ISpatialContainerManager, implemented by SpatialRuntimeService.apk in the com.pico.spatial.runtime_service apex) turns each container's SurfaceFlinger layer into a 3D quad; com.picoxr.systemui:decor draws the caption bar/chrome (a 600x208 caption-bar window with captionBarContainerId=45 existed for Settings). All 2D windows live on Display 0 (2160x2158); Display 2 is only a private 10x10 VirtualDisplay owned by com.pxr.scenarioprovider (the Unity environment renderer). The user's earlier 'does not composite' observation was a camera-pose artifact (the known C2 free-cam drift) — the panel spawns at the shell dock position. The Spatial SDK exposes the same system app-side: SpatialContainerManager.openWindowContainer/openStageForResult with WindowContainerProperties (size w/h/depth, PLANAR/VOLUMETRIC form, caption bar, anchor-relative placement), plus SHARED_SPACE vs FULL_SPACE semantics via android.app.SpaceContext. Strategic bonus: a WindowContainer panel is a normal Android activity, so real Compose/View UI with live runtime text can render inside the spatial viewport — bypassing the 'no public TextComponent' limitation of the 3D scene.

## Android Studio plugin — feasible: **partial**

The PICO Android Studio plugin (org.byted.ide.spatial, "PICO Spatial (CN)" 0.13.2, in AndroidStudio2025.1.4/plugins/SpatialPlugin) is confirmed UX-only, with one correction to the prior finding: the AS plugin itself never invokes ide_build.sh — the headless spatial-asset build is owned entirely by the Gradle plugin com.pico.spatial.tools:0.13.1 (SpatialPackTask), which launches the Spatial Editor binary with --ide_noGraphics/--ide_buildOutputDir/... flags; ide_build.sh is just a lock/IPC wrapper around that same invocation, and PICO-MCP's src/editor.ts already drives the binary directly. The plugin registers only IDE conveniences: a project wizard, an asset-import action, a JOGL 3D scene-preview editor, a toolbox/SDK-manager tool window, and a deviceProvisioner that surfaces the PICO emulator as a run target — there is NO custom run configuration type, no gradle task injection, and no external CLI/IPC surface. Its 8 self-defined extension points are internal AS-version adapters implemented by the plugin itself, undocumented and unstable. The only reusable artifact is the bundle of FreeMarker project templates + SpatialResourceProject.zip skeletons inside the jar. Verdict: the Gradle/CLI layer is strictly better for automation; building on the AS plugin offers zero capability the MCP does not already have headless.

## Spatial Editor — feasible: **partial**

The PICO Spatial Editor 0.13.4 is NOT Electron — it is a native Qt 6/QML app (bundle id com.bytedance.pico.x_birdApp, internal codename "xBird", 89MB binary, own spatial.engine + MaterialX + MoltenVK; no app.asar/package.json anywhere). There is no official, documented third-party plugin API (no plugins/ dir is scanned, no manifest schema doc, no extensions UI), but the editor is internally built as ~20 Qt/QML plugins (spatial_editor::xbird::{Viewport,Inspector,Timeline,Dock,...}Plugin) and exposes several real, working extension surfaces: (1) a data-driven CUSTOM ECS COMPONENT system — per-project `.Component/component.json` registry plus `.spatialEditorComponent` JSON definitions (keys: package/properties/dataType/defaultValue; types bool/string/number/vec3/vec4/quat/uint32/float3/int3/bool3) that the Inspector auto-renders via QML property editors and hot-reloads via a file watcher (editor-side code complete: CustomComponentWrapper.cpp, IDECustomComponentConfig, EditorCustomComponentElementConfig — the Kotlin-side exporter is not shipped in the local SDK, mirroring Meta's .metaspatialcomponent pattern); (2) an AUTOMATION/IPC surface — headless CLI (`--project= --ide_noGraphics --ide_buildOutputDir= --ide_buildResultName= --ide_buildSpecialScenes= --ide_resultCodeFile= --ide_buildAdditivePath=`, plus --ide_preview/--ide_pid/--scene=) and a named-pipe command channel (`__IdePipe__Editor`/`__IdePipe__Ide`, driven by ide_build.sh: a running editor accepts flag-strings written to the pipe) — this is exactly how the Android Studio integration drives it; (3) native Qt plugin drop-in points — standard Contents/PlugIns categories (assetimporters currently holds libassimp.dylib; any conforming Qt plugin dylib placed there loads) and a shipped proof-of-concept hot-loadable plugin `libxBird_hotfix_plugins.dylib` (Qt plugin IID `com.hotfix.commoninterface`, class CommonPlugin) — though adding dylibs invalidates the code signature unless re-signed; (4) data-driven config/content files read at runtime: inspectorconfigs/componentList.json (explicitly models componentType SYSTEM/APPLICATION/PLUGIN with belongTo "ThirdParty"), resources/materialx/libraries (MaterialX node libraries + nodeDesc.json/nodeDef.json UI descriptors), resources/builtin/config/{effects,container}.json, effect_templates.db and shader_sdk.db (unencrypted SQLite file_info blob stores), and config/modules.json (remote asset-library endpoints pico-drop*.picoxr.com, tracy profiler port 8088). The binary also embeds a Squish GUI-automation hook (SQUISH_AUT_PORT/SQUISH_PREFIX). The project format itself is open (JSON .spatialproject + USDA scenes + .picometa sidecars) and file-watched, so external tools can inject content live. Data dir ~/Library/Application Support/Spatial Editor holds only prefs/telemetry — no plugin loading from there.

**Extensibility points:**
- Custom ECS components: <project>/.Component/component.json registry + .spatialEditorComponent JSON files (keys: package, properties, dataType, defaultValue, displayName, elements, componentName, packageName; types: bool/string/number/vec3/vec4/quat/std::uint32_t/float3/int3/bool3) — Inspector auto-renders via qrc:/spatial.engine/imports/x_bird/Inspector/element/{number,bool,string,vec3,vec4}Property.qml and hot-reloads on file change (InspectorController onFileChange)

Defer in-process work: the Qt PlugIns drop-in and the com.hotfix.commoninterface hotfix-plugin path are real but unofficial, signature-breaking, and version-fragile; only pursue them if UI panels inside the editor become a hard requirement.

## Gradle plugin — feasible: **yes**

Yes — we can cleanly build our own Gradle plugin that hooks around PICO's pack pipeline. The plugin (com.pico.spatial.tools:0.13.1, entry class com.pico.spatial.tools.SpatialPackPlugin, cached at ~/.gradle/caches/modules-2/files-2.1/com.pico.spatial.tools/..., served from the Volcengine maven repo declared in showroomxr-native/settings.gradle.kts; ~/Library/PICO/sdk holds only the editor app + spatialbundle CLI, no maven artifacts) registers a 'spatial' extension (SpatialPackConfig: name/outDir/spatialToolsVersion/spatialEditorDirectory/useSpatialBundleTool/bundleOptions{forceBuild,useBundleIncremental,files.include}/bundles{} NamedDomainObjectContainer<BundleConfig>) and creates SpatialPackTask instances: spatial_pack_task_base eagerly in apply(), then in afterEvaluate an umbrella spatial_pack_task plus spatial_pack_task_<bundleName> per DSL bundle. Per variant it wires generate<Flavor><BuildType>Assets.dependsOn(pack), mergeAssets.dependsOn(pack) + doFirst/doLast asset-splice actions, compress...Assets doFirst/doLast, and a preBuild.doFirst validation — that is how it auto-rides assemble. The task's @TaskAction reads the single <module>/src/main/res3d/*.spatialproject (needs >=1 .usda), shells out to ~/Library/PICO/sdk/<ver>/editor/spatialbundle/spatialbundle pack -p, and writes <name>.bundle into src/main/assets/ (md5 cache key in intermediates spatial/bundle/cache_key). There is no public action-registry (IAction/BaseSpatialAction exist but the pipeline is hard-coded), so the supported extensibility seam is the Gradle task graph: because their tasks are created eagerly by name, a live tasks.matching { name.startsWith("spatial_pack_task") }.configureEach { dependsOn(ourBakeTask); doLast { verify } } wiring inside plugins.withId("com.pico.spatial.tools") is ordering-robust regardless of which afterEvaluate runs first. Consumption in showroomxr-native confirms the pattern: only the :editor-asset library module applies the plugin (editor-asset/build.gradle with spatial { name = "editor-asset" }); the app just packages the module, and the root already applies a custom pico.gradle.kts proving external task injection works in this project.

**Extensibility points:**
- Task names to hook: spatial_pack_task_base (SpatialPackTask, created eagerly in Plugin.apply), umbrella spatial_pack_task + spatial_pack_task_<bundleDslName> (created in project.afterEvaluate) — all match name.startsWith("spatial_pack_task")
- Cleanest pre-hook: tasks.matching { it.name.startsWith("spatial_pack_task") }.configureEach { dependsOn(ourBakeTask) } inside project.plugins.withId("com.pico.spatial.tools") — live collection, immune to afterEvaluate ordering
- Cleanest post-hook: doLast on the same pack tasks (runs before PICO's mergeAssets doFirst splice), or finalizedBy(ourVerifyTask) for non-blocking checks; mergeAssets (variant.mergeAssetsProvider, MergeSourceSetFolders) already carries PICO's SpatialMergeAssetsFirst/LastAction doFirst/doLast and dependsOn(pack)
- Pre-build validation seam: preBuild.dependsOn(ourValidateScenesTask) — PICO itself only adds preBuild.doFirst, and task dependencies always run before doFirst actions
- Input contract for an auto-bake task: write USD content into <module>/src/main/res3d/<one>.spatialproject before pack; must contain >=1 .usda (usdz-only is rejected with an explicit error); mutating it invalidates their md5 cache key (intermediates spatial/bundle/cache_key) so re-pack is automatic
- Output contract for a verify task: <module>/src/main/assets/<name>.bundle (default) or spatial { outDir } / per-bundle BundleConfig.outDir
- DSL to read from our plugin: project.extensions.findByName("spatial") as SpatialPackConfig (registered via extensions.create("spatial", SpatialPackConfig::class, project) in PluginExt.createSpatialPackConfig) — fields name/outDir/spatialToolsVersion/spatialEditorDirectory/useSpatialBundleTool/bundleOptions/bundles; depend on the jar as compileOnly("com.pico.spatial.tools:com.pico.spatial.tools.gradle.plugin:0.13.1") from https://artifact.bytedance.com/repository/Volcengine
- Reactive application: project.plugins.withId("com.pico.spatial.tools") { ... } — plugin id from META-INF/gradle-plugins/com.pico.spatial.tools.properties (implementation-class=com.pico.spatial.tools.SpatialPackPlugin)
- Designed-for-extension types (but no public registry): interface IAction { perform(IActionContext) }, interface IActionContext { project/config/putData/getData }, abstract BaseSpatialAction; SpatialPackTask is non-final with public setPackTask/setBundleConfig/setActionContext + @TaskAction executeTask — subclassing possible but unsupported/fragile; prefer graph wiring

- AGP hooks PICO uses (old variant API): AppExtension.applicationVariants / LibraryExtension.libraryVariants .all in afterEvaluate; generate<Flavor><BuildType>Assets and compress<Flavor><BuildType>Assets located by findByName with getTaskName(buildType)=capitalized build type
- Consumer files: /Users/sushantsrikrish/AndroidStudioProjects/showroomxr-native/editor-asset/build.gradle (applies plugin + spatial{} block), settings.gradle.kts (Volcengine repo), build.gradle.kts (applies custom pico.gradle.kts — existing proof that injecting our own tasks at the root works), app/build.gradle.kts (does NOT apply the plugin; consumes :editor-asset + noCompress '.bundle')
- Plugin jar path: /Users/sushantsrikrish/.gradle/caches/modules-2/files-2.1/com.pico.spatial.tools/com.pico.spatial.tools.gradle.plugin/0.13.1/d6da67570fee8bc92367b5fbe4caca55946f2e2c/com.pico.spatial.tools.gradle.plugin-0.13.1.jar (0.12.0 also cached)

**Recommendation:** Build a small convention plugin (e.g. id "com.pico.hooks") delivered as a composite build (includeBuild) or mavenLocal artifact, applied next to com.pico.spatial.tools on the editor-asset module. In apply(): project.plugins.withId("com.pico.spatial.tools") { register two tasks — (1) bakeSpatialAssets: auto-bake/generate USD content into src/main/res3d/<x>.spatialproject (guarantee >=1 .usda), (2) validateSpatialScenes: lint the .usda scene graph (run preflight_lint-style rules) — then wire tasks.matching { it.name.startsWith("spatial_pack_task") }.configureEach { dependsOn(bake, validate); doLast { assert the emitted .bundle exists/size/manifest in src/main/assets or spatial.outDir } } and preBuild.dependsOn(validate) }. This is ordering-robust (live matching survives PICO's afterEvaluate eager task creation), touches zero PICO internals beyond stable task names, and slots directly into `assemble` because AGP's generate/merge-assets tasks already depend on the pack tasks. First deliverable: the validateSpatialScenes pre-gate (fails the build on a bad scene before the spatialbundle CLI ever runs), since it reuses existing PICO-MCP lint logic and proves the hook end-to-end with `./gradlew :editor-asset:assembleDebug`.
