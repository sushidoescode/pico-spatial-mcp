# V3.2 EDITOR AUTOMATION MAP — what's headless vs GUI-only (recon 2026-06-14)

> Produced by the `spatial-editor-recon` workflow (6 read-only investigators + synthesis).
> The honest spike result that v3.2 is built on. **`generate_agent_bridge` already SHIPPED**

## Summary

The Spatial Editor's automation surface is BUILD-CENTRIC and one-directional: the only first-class headless entrypoint is the editor's own `--ide_noGraphics` full-project build (proven in production by build_spatial_project, and by the editor's own ide_build.sh which the Android Studio plugin uses). There is NO scripting console, no RPC/gRPC/WebSocket control port, no QML automation hook, and no per-operation API. The single most important finding for v3.2: "drive the editor itself" decomposes into a HEADLESS half that is fully buildable now (project build + bundle pack + bundle/project decode + a config/USD file-edit lever layer that the agent edits then rebuilds to verify) and a GUI half (material authoring, component wiring, timeline keyframing) that has NO headless or file-replay path and must stay GUI-only or be emulated by direct USD/JSON authoring + rebuild. The honest framing of editor_op is therefore: it is NOT a generic "perform any editor action headlessly" tool — it is "edit a decoded file lever (EditorEnvSettings.json skyboxColor/useColor/intensityExponent/rotation, EditorContainerSettings.json sizes/containerType, or scene USDA prims) then re-run the headless build, and diff the decode to confirm". Verification stays code/file-level (decode_editor_project, inspect_bundle, decode_spatial_bundle); visual verification remains the unsolved C2 wall — the best lead is passing a populated previewConfig JSON to ScenePreview rather than the empty {} the MCP sends today, but whether ScenePreview honors those fields is UNVERIFIED and must be spiked on a live emulator before any tool claims deterministic capture.

## Headless-scriptable (buildable now)

- Full .spatialproject build via editor `--ide_noGraphics` — args: --project=, --ide_buildOutputDir=, --ide_buildResultName=, --ide_buildSpecialScenes=, --ide_resultCodeFile=, --ide_buildAdditivePath=; result JSON {"data":{"code":"10000"...}}. EVIDENCE: editor.ts:166-203 (build_spatial_project, in production) + ide_build.sh:248-251 (same path the AS Gradle plugin uses). All --ide_* flags confirmed present in the editor binary strings table.
- Scene->bundle pack via spatialbundle CLI (no GUI, no Gradle): `pack -s <dir> -o <out> --formats usda|usdc|usdz|usd|gltf|glb [--compress-textures astcNxN] [--force-build] [--incremental-build] [--scene-files] [--exclude-dirs] [--texture-dir] [--preserve-resources] [--discard-unused-resources]`. EVIDENCE: bundle.ts:37-49 (pack_bundle) + EMPIRICALLY verified `spatialbundle pack --help` (this session). Note: --compress-textures is marked [required] in the binary usage line — pack_bundle passes it only when !=none, which works in practice but is worth re-checking.
- Bundle inspection: `spatialbundle info -i <bundle>` (read-only) + extracting BundleInfo.json/AssetInfo.json from the .bundle zip. EVIDENCE: bundle.ts (inspect_bundle, decode_spatial_bundle). CORRECTION: the `--details` flag claimed by one report does NOT exist — empirical `info --help` shows only -h/--help.
- Static project X-ray with no editor running: decode_editor_project parses .spatialproject, ModelView, every scene USDA (prims/materials/shaders/components/asset-refs), Sources/Assets, .Library/.Component/.CacheData. EVIDENCE: editorproject.ts:98-130. GAP: it does NOT yet parse the UserSettings ECS files (EditorEnvSettings.json, EditorContainerSettings.json, EditorViewportSettings.yaml, EditorSceneSettings.yaml, history.json) — confirmed by grep this session.
- Config/USD file-edit lever layer (the real basis for a headless `editor_op`): edit committed-to-git ECS JSON (EditorEnvSettings.json: skyboxColor RGBA, useColor, intensityExponent, rotation, environmentIdx; EditorContainerSettings.json: planeSize/volumeSize/containerType) or scene USDA prims, then re-run the headless build. EVIDENCE: project-settings report decode of both ECS JSON files in claimsight-native, plus .gitignore proving these two are shared/committed while the YAMLs are per-user.
- ScenePreview deploy: install ScenePreview.apk, push bundle, `am start .platform.LaunchActivity`, broadcast com.pico.spatial.editor.scenepreview.FILE_TRANSFER_COMPLETE with filePath/sceneName, then adb screencap. EVIDENCE: editor.ts:207-276 (preview_scene). Capture is guest-framebuffer only (2D), not the composited 3D stage.
- IPC build into an ALREADY-OPEN editor of the same version: write the --project/--ide_build* arg line to a FIFO. EVIDENCE: ide_build.sh:259-262. CRITICAL CAVEAT: the pipe path is argument $8 (IDE_PIPE_PATH), NOT a fixed/discoverable path — the CALLER must create the named pipe and the running editor must already be listening on it; the MCP has no evidence the editor opens a discoverable FIFO on its own, so this is only usable if we replicate the Gradle plugin's exact handshake. Treat as unverified-by-us.

## File-edit levers (the real basis for a headless editor_op)

- EditorEnvSettings.json `skyboxColor` {x,y,z,w} RGBA 0-1 -> background/skybox color when useColor=true. Committed to git (shared). SAFEST deterministic lever. PATH: <project>/UserSettings/EditorEnvSettings.json.
- EditorEnvSettings.json `useColor` bool -> toggle solid-color vs IBL background. CAUTION: false + originImage="" falls back to default.
- EditorEnvSettings.json `intensityExponent` float -> environment lighting brightness (observed -24 = very dark). Note negative-exponent semantics are inferred, not proven.
- EditorEnvSettings.json `rotation` float -> IBL/skybox Y-rotation (degrees vs radians UNVERIFIED).
- EditorEnvSettings.json `environmentIdx` int -> preset environment selection (range unknown).
- EditorContainerSettings.json `planeSize`/`volumeSize` TVector3<int> -> preview container dimensions in device points. Committed to git.
- EditorContainerSettings.json `containerType` string -> "Stage"|"Plane"|"Volume" layout mode (non-Stage values UNVERIFIED to be accepted).
- Scene USDA prims (Sources/Scenes/*.usda) -> the real authoring surface for geometry, transforms, materials, and declarative components; edit then headless-build. This is where author_materialx / collider / component tools already write.
- EditorViewportSettings.yaml `camerasConfig[].Pos`/`Rotation`/`RoamRadius` -> editor 3D viewport camera pose. GIT-IGNORED (per-developer) — safe for agent automation but does NOT travel with the project and does NOT affect the built bundle.
- DO-NOT-EDIT class: __index/__elindex/__type/__eltype ECS hints, .CacheData/* and .Library/* (auto-regenerated), and any sceneGuid cross-reference unless ALL linked files are updated together.

## GUI-only (no headless/file path found)

- Material authoring/graph editing in the MaterialEditor — no headless analog; MaterialX is baked at `spatialbundle pack` time against a FIXED built-in IBL (SystemIbl_ibl_brightness.ktx), with no runtime/headless IBL setter. The only file-level proxy is hand-authoring .mtlx (author_materialx), but hand-authored <image> texture nodes render BLACK at runtime — only the editor-authored path or bake_textured_model (GLB->bundle) produces working textures. EVIDENCE: materialx-ibl report + materialx.ts:19-20 comment.
- Component wiring / attaching SpatialComponent instances through the editor GUI — the plugin layer (spatialComponent/spatialTimeline/spatialAudio dylibs) is a pure DECLARATIVE USD schema layer, statically linked, with no runtime plugin API. You can hand-author the USD prims (SpatialComponent/SpatialStruct), but see the cooked-physics caveat below. EVIDENCE: engine-scripting report.
- Timeline keyframing (SpatialTimelineTrack/Action) — GUI-only authoring; only the declarative schema is exposed. EVIDENCE: component-formats report.
- Interactive 3D viewport / free-camera control in the qemu emulator window (C2) — uncontrollable headlessly (no Quartz/cliclick; requires a mouse-drag to enter camera mode). EVIDENCE: hostgui.ts gui_camera + MEMORY C2.
- Any generic 'perform editor action and have it persist into the project' beyond the file levers — there is no operation log, no macro/replay, no console (no Python/Lua/JS beyond QML's internal engine), no Tracy command channel (port 8088 is read-only telemetry). EVIDENCE: engine-scripting report §3,4,7.

## Decoded editor component USD formats (+ typeId registry)

- CollisionComponent — `def SpatialComponent "CollisionComponent"`, info:id="CollisionComponent", info:typeId=10170138008305910195; contains `def SpatialStruct "shapes0"` {float3 center, uint64 id, info:typeId=4878244361267076049 (CollisionShape struct), bool isConvexMesh, quatf rotation, float3 size, token type="BOX", nested `def SpatialStruct "mesh"` info:typeId=7578755580861454209 with parent_resource_id/resource_id}. SOURCE: MyScene.usda:463-486.
- SpatialTimeline schema family (schema.usda): SpatialTimeline{int order}, SpatialTimelineTarget{int order}, SpatialTimelineTrack{int order}, SpatialTimelineAction{uniform token info:id; string actionKind; double startTime=0; rel target}.
- SpatialAudio schema family (schema.usda): SpatialAudioFile{asset file; token loadingStrategy=preload|stream; token normalization=none|dynamic; token calibrationMode=none|absolute|relative; token playMode=random|forward|backward; bool shouldLoop; bool shouldRandomizeStartTime; rel mixerGroup}, SpatialAudioMixerGroup{float gain; float speed; bool mute}.
- Baked scene-data typeId registry (cache.bundle 103.scene.data): 238735827=CollisionComponent, 1214404487=MaterialKeepComponent, 3730430948=ModelComponent, 4066030039=TransformComponent. These are DIFFERENT integers from the USD info:typeId values — the bake reassigns typeIds.
- Cooked physics binaries (NOT USD text): 87/100.collisionshape.data = C++ struct spatial::physics::CollisionShapeAssetData_v1 (TVector3 center/size, TQuaternion rotation, MeshResource ref); 86/99.physicsmaterial.data = spatial::physics::PhysicsMaterialAssetData_v1 (friction/restitution from editor GUI defaults, NOT USD attrs). CAVEAT: per DESIGN.md, a hand-authored USD CollisionComponent prim is an editor-internal hint that the runtime does NOT turn into a live PhysX query actor — colliders must be set on a live entity at runtime. So authoring collision via USD+rebuild will NOT yield queryable physics; it only populates the cooked asset for editor-managed paths.
- EditorEnvSettings.json ECS shape: {__type: spatial_editor::xbird::ecs::EnvironmentSettingComponents, vectors.__elements[]{environmentIdx:int, intensityExponent:float, originImage:string, rotation:float, sceneGuid:uuid, skyboxColor: TVector4<float>{x,y,z,w}=RGBA, useColor:bool}} with __index/__elindex/__eltype binary-deser hints that MUST NOT be edited.
- EditorContainerSettings.json ECS shape: {__type: ViewportContainerSettings, vectors.__elements[]{containerType:"Stage"|..., planeSize:TVector3<int>, volumeSize:TVector3<int>, unitType:"DevicePoint", showUISample:bool, sceneGuid:uuid}}.

## Deterministic capture approach (C2 — still a SPIKE, unverified)

Best candidate: extend preview_scene to pass a POPULATED previewConfig JSON instead of the empty `{}` it sends today (editor.ts:251,257 hardcode `previewConfig {}`). Candidate fields decoded from ScenePreview's classes.dex string table: cameraDistance, cameraHeightOffset, boundingSphereRadius, createCameraTarget, and possibly fov/lookAt (LookAtComponent + SpatialViewPointManager exist in the dex). If honored, this gives a fixed, repeatable framing for verify_visual. HONEST CAVEAT (do not ship as 'deterministic' yet): (1) ScenePreview honoring these fields is UNVERIFIED — they appear in the string table but the MCP has never exercised them, so a live-emulator spike is mandatory before any tool claims deterministic capture; (2) even if framing works, adb screencap captures the GUEST framebuffer (display 0 = 2D home env + 2D panels) and the immersive 3D stage is HOST-COMPOSITED, NOT in that framebuffer (ROADMAP Appendix B), so a controlled previewConfig may still not surface 3D content via screencap — the spike must diff both adb screencap AND gui_capture to learn which (if either) reflects the camera change. Until that spike passes, verification for v3.2 stays code/file-level: decode_editor_project + inspect_bundle + decode_spatial_bundle, with visual verification explicitly flagged headset-only.

## Prioritized v3.2 tool build list

- **[P1] editor_build_project (promote/harden build_spatial_project)** (headless) — The authoritative headless full-project build with GUI parity (components/timelines baked). Already exists as build_spatial_project; v3.2 work = robustify result-code handling, surface the result JSON verbatim, and document the lock-file protocol.
  - evidence: editor.ts:166-203 in production; ide_build.sh:248-251 confirms it is the AS plugin's exact path; all --ide_* flags present in editor binary strings.
  - risk: Low. Known wall: project must NOT be open in a running editor (lock-file check at editor.ts:74-85); if open in same version, only the FIFO/IPC path works and that path is unproven by us.
- **[P1] editor_project_diff** (headless) — Decode a project before and after an edit/build and report the structural delta (scenes, prims, components, asset inventory, .CacheData manifest md5/scene-list, baked material count). This is the verification backbone for every file-edit op and replaces the missing visual check.
  - evidence: decode_editor_project already extracts all needed fields (editorproject.ts:98-130); diff is pure file-level computation over two decode snapshots.
  - risk: Low. Honest limit: a diff proves the build/decode CHANGED, not that the experience changed — pair with the headset-only flag for anything visual/physical.
- **[P2] decode_editor_settings (extend decode_editor_project)** (file-edit) — Parse the UserSettings ECS files (EditorEnvSettings.json, EditorContainerSettings.json, EditorViewportSettings.yaml, EditorSceneSettings.yaml, history.json) so the agent can READ current env/viewport/container state before editing — the prerequisite for a safe editor_op.
  - evidence: project-settings report fully decoded both ECS JSON files; grep this session confirms editorproject.ts does NOT yet read them.
  - risk: Low. ECS __index/__elindex offsets vary per struct; parser must treat them as opaque and never rewrite them.
- **[P2] editor_op (file-lever variant, NOT generic action automation)** (file-edit) — Apply a whitelisted, decoded file lever (EditorEnvSettings skyboxColor/useColor/intensityExponent/rotation; EditorContainerSettings sizes/containerType; or scene USDA prim edits) then re-run editor_build_project, returning an editor_project_diff. This is the honest 'drive the editor' mechanism given there is no action API.
  - evidence: project-settings report (committed-to-git ECS files + .gitignore proving they are shared); engine-scripting report VERDICT confirms no console/RPC/QML hook exists, so file-edit+rebuild is the ONLY drive path.
  - risk: Medium. Field semantics partly inferred (intensityExponent sign, rotation units, containerType non-Stage values UNVERIFIED); must guard sceneGuid cross-refs and never touch __ ECS hints or git-ignored YAMLs as if shared. Cooked physics: USD-authored CollisionComponent will NOT become a live PhysX actor (DESIGN.md) — flag headset/runtime caveat.
- **[P3] editor_export_bundle (consolidate pack_bundle + inspect_bundle)** (headless) — Scene-dir -> .bundle via spatialbundle pack with the verified flag set, immediately followed by spatialbundle info + AssetInfo decode for a self-verifying export. Faster than a full project build when no editor-managed features are needed.
  - evidence: bundle.ts:37-49 + empirically verified `spatialbundle pack --help`/`info --help` this session.
  - risk: Low-Medium. CORRECTIONS to prior reports: --material-platform and `info --details` do NOT exist in this binary; --compress-textures is marked [required] in usage — verify the no-compression path still parses.
- **[P4] preview_scene_with_camera (SPIKE before committing as a tool)** (unknown) — Pass a populated previewConfig (cameraDistance/cameraHeightOffset/boundingSphereRadius/createCameraTarget, maybe fov/lookAt) to ScenePreview to attempt a deterministic framing, diffing adb-screencap vs gui_capture to learn what is honored and what surfaces.
  - evidence: ScenePreview dex contains these fields + LookAtComponent + SpatialViewPointManager; editor.ts:251,257 currently hardcode previewConfig {}.
  - risk: High/unproven. Fields may be ignored; immersive 3D stage is host-composited and absent from the guest framebuffer (ROADMAP Appendix B). Do NOT label any output 'deterministic capture' until the live-emulator spike confirms it. Keep as a spike, not a shipped guarantee.

## Open questions (need a GUI experiment or hardware)

- Does the running editor expose a discoverable FIFO for the IPC build path, or must the caller create the named pipe AND the editor already be listening on a caller-supplied path? ide_build.sh shows IDE_PIPE_PATH=$8 (caller-supplied), with no evidence the editor self-opens a known pipe — needs a GUI experiment (open a project, then attempt the printf-to-FIFO handshake).
- Will ScenePreview actually honor a populated previewConfig (cameraDistance/fov/lookAt), and if so does the resulting frame land in the adb-screencap guest framebuffer or only in the host-composited gui_capture? Requires a live-emulator spike; this is the gate for any deterministic visual verification (C2).
- Are EditorEnvSettings/EditorContainerSettings edits actually consumed by the headless `--ide_noGraphics` build, or are they only read by the GUI at open time? If headless ignores them, editor_op's env/container levers only affect the GUI session, not the built bundle — must verify by build-then-decode diff.
- intensityExponent semantics (is -24 darker than 0? linear vs log?) and rotation units (degrees vs radians) are inferred from a single sample — need a controlled before/after to calibrate.
- containerType values other than "Stage" ("Plane"/"Volume") are assumed valid but unverified to be accepted by the editor/runtime.
- --ide_preview and --ide_pid flags exist in the binary but have no documented build semantics — unknown whether --ide_preview offers any headless render/preview capability that could sidestep ScenePreview.
- Whether spatialbundle pack's [required] --compress-textures truly rejects omission (the MCP omits it for compress=none) — empirically the MCP path works, but the usage line implies it is mandatory; reconcile.
